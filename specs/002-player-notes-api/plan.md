# Implementation Plan: Player Notes API

**Branch**: `002-player-notes-api` | **Date**: 2026-04-01 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/002-player-notes-api/spec.md`

## Summary

REST microservice for managing per-session notes about players. Each note is scoped to an
authenticated session (JWT `sub`) and a target player (`uniqCode`). Core rules: one active note
per (author, player) pair; max 100 active notes per session; 30-day TTL with unlimited extensions;
note content is an arbitrary JSON object (≤ 10 KB). Built with Java 21 + Spring Boot 3.x,
Spring Security 6 JWT (HS256), Spring Data JPA, and a scheduled cleanup job.

## Technical Context

**Language/Version**: Java 21
**Primary Dependencies**: Spring Boot 3.x, Spring Security 6 (OAuth2 Resource Server / HS256),
  Spring Data JPA, Hibernate, Bean Validation (Jakarta), Jackson, Spring Boot Actuator,
  Nimbus JOSE+JWT (transitive via Spring Security)
**Storage**: H2 in-memory (dev/local), PostgreSQL (production); Flyway for prod migrations
**Testing**: None — explicitly out of scope per constitution
**Target Platform**: Linux server (JVM)
**Project Type**: REST web service
**Performance Goals**: All API operations respond within 1 second (SC-003)
**Constraints**: Max 100 active notes per session; max 10 KB per note (UTF-8); JWT locally
  validated; no rate limiting beyond the 100-note cap
**Scale/Scope**: Single-instance microservice for v1; no distributed state

## Design Decisions

### Authentication
- Spring Security 6 OAuth2 Resource Server with HS256 JWT.
- `JwtDecoder` bean via `NimbusJwtDecoder.withSecretKey()` — no auto-config property for
  symmetric keys; bean declared explicitly in `SecurityConfig`.
- `authorId` = `jwt.getSubject()` accessed via `@AuthenticationPrincipal Jwt`.
- Secret injected via `APP_SECURITY_JWT_SECRET` environment variable (Base64, ≥ 256 bits).

### Content Validation
- JSON object check: `objectMapper.readTree(content).isObject()` — rejects arrays,
  primitives, null, malformed JSON.
- Size check: `content.getBytes(StandardCharsets.UTF_8).length <= 10_240` — done before
  JSON parse to short-circuit early.
- Both checks performed in `NoteService` before any persistence call.

### Uniqueness Enforcement
- Primary guard: `noteRepository.existsByAuthorIdAndUniqCodeAndExpiresAtAfter(authorId, uniqCode, now)` → HTTP 409 on conflict.
- No DB-level partial unique index (PostgreSQL does not support volatile `NOW()` in index
  predicates). Any unexpected DB integrity violation caught and mapped to 409 as fallback.

### Note Limit
- Check: `noteRepository.countByAuthorIdAndExpiresAtAfter(authorId, now) >= 100` → HTTP 422.
- Checked before uniqueness check (limit is a harder gate).

### Expiry Lifecycle
- `expiresAt` = `createdAt + 30 days` on creation.
- `expiresAt` = `now + 30 days` on extend — always reset from current moment, not from
  current `expiresAt`.
- All queries filter `expires_at > now` — expired notes invisible to API.
- Background job (`ExpiredNoteCleanupJob`) runs daily at 02:00 via `@Scheduled(cron)`;
  deletes rows where `expires_at < now`.

### List Response
- Ordered `ORDER BY created_at DESC` at query level (`@Query` or derived method name).

### Error Responses
- `GlobalExceptionHandler` (`@RestControllerAdvice`) maps all custom exceptions and
  validation errors to `ErrorResponse` with `status`, `error`, `message`, `timestamp`.

### DB Index
```sql
CREATE INDEX idx_notes_author_active
    ON notes (author_id, expires_at DESC, created_at DESC);
```
Supports: active-note list, count check, uniqueness check — all in one composite index.
